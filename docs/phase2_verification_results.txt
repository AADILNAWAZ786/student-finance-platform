5. What the Phase 2 tests verify (summary)
-------------------------------------------
Models (65 + 16 contract): every CHECK, unique and PROTECT rule on the five tables; no DB unique
    on invoice→enrollment (duplicate must be representable); staged LedgerEntry = the
    DATABASE_DESIGN.md table minus exactly scholarship_allocation (Phase 3), payment and
    refund (Phase 4), and their 4 entry types; the other four tables match the design
    exactly (columns, lengths, decimal precision, FK targets, enums), read from the frozen doc.
Calculators (26 + 44 acceptance): price_lines frozen 2-argument signature (D4); apply_waivers
    (BR-WAV-01); late fee at the grace boundary, ₹500/₹5,000 limits, half-up rounding;
    ledger_balance (D13, exact Decimal); open amounts; void plan; all six collection statuses.
Services (29 fee schedules + 67 billing): D3 residency mapping, D5 flags, version chain rules,
    D2 required fee types (each missing type → 422), BR-FEE-01 version on the invoice date,
    BR-INV-01 duplicate (409, nothing written, ID counters untouched), regeneration after
    void, D11 (COMPLETED → 409), waivers, zero-priced invoice, atomic rollback when a ledger
    post fails mid-way, void (−net adjustments, ledger back to 0, BR-INV-08 current-amount
    rule incl. fully reversed allocations allowed), D15 dates, late fees (once, dry run,
    date-independent), refresh (due date boundary, never backwards, VOID skipped), balance
    and the BR-BAL-02 identity.
API (63): every endpoint, filters (incl. in_force_on), money as strings only, server-field
    rejection, 400/404/405/409/422 envelopes, D14 (no fee-schedule detail), POST-only batches,
    every success response validated against the served OpenAPI schema.
Verification: routes 23 (11 + 12) × every method; all 112 documented error examples (56
    Phase 1 + 56 Phase 2) replayed live and equal; role matrix incl. D6 for 13 billing
    operations; zero queries on ground_truth for every billing call; ground_truth holds no
    billing table; migration safety; two concurrent generations → exactly one invoice and one
    409 DUPLICATE_INVOICE (file database, two threads); identical rows (IDs included) when
    the same scenario runs twice; every invariant reconciliation will re-check (ledger 1:1 and
    signs, gross/net/waiver arithmetic, invoice total, open ≥ 0, event chains, stored status =
    BR-INV-06 at collection_status_as_of, BR-BAL-02 per student).
