6. Concurrency (ARCHITECTURE §8.2), file-based test DB, transaction=True
------------------------------------------------------------------------
Two threads released together by a barrier; any "database is locked" fails the test.
    two AUTO allocations of one payment       -> ALLOCATED + NO_FUNDS_AVAILABLE; Σ = payment
    two payments, one line (LAB 6,000)        -> one ALLOCATED, one ALLOCATION_EXCEEDS_LINE_OPEN
    two refunds from one payment (30,000)     -> one REQUESTED, one REFUND_EXCEEDS_PAYMENT_AVAILABLE
    refunds sharing one credit balance        -> reservations hold (loser: CREDIT_BALANCE)
    two approvals of one refund               -> APPROVED + ILLEGAL_TRANSITION
    one external_reference twice              -> one payment + DUPLICATE_PAYMENT
    scholarship apply vs payment on one line  -> APPLIED either way; line open >= 0; identity
Result: 7 passed, 3 consecutive runs.
Negative control (scratch settings only, never committed): with transaction_mode DEFERRED the
same 7 tests all FAIL ("database is locked"), so the tests do detect a broken lock strategy.

P4-B1  Payment.save() refuses any update of a persisted payment (AppendOnlyError);
       inserts unchanged.

       refund_id, student, payment, payer_type, enrollment, reason, amount, requested_date,
       calculation or recorded_at (or update_fields naming one) raises AppendOnlyError before
       anything is written; only the two mutable columns are written. Loaded values are
       deep-copied, so an in-place change to the calculation dict is also refused (the first
       version of the guard missed this; the new test caught it before delivery).

       (no add, change or delete permission, even for a superuser).
